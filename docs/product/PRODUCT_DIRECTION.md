# UW 产品方向与长期开发基线

- **状态**：Current / 唯一产品方向
- **版本**：0.5.0-pre-capture planning baseline
- **更新日期**：2026-08-07
- **适用范围**：产品、剧情、美术、程序、音频、QA 和后续智能体

## 1. 产品目标

UW 要做成一款面向大众、容易上手、内容完整、可重复游玩且能够持续扩展的 2D 叙事 RPG。第一阶段先完成一条可信、紧凑、可回放的 Alicization 前期主线，后续再扩展战斗、地图、角色成长和更大的世界。

最终质量目标不是“能运行的剧情 Demo”，而是具备完整 RPG 产品所需的内容密度、交互反馈、角色动作、贴图层次、音频、战斗规则、存档兼容和持续制作管线。

## 2. 体验支柱

1. **生活感**：玩家每天有明确目标，也有自由安排时间、地点、活动和关系的空间。
2. **选择有后果**：活动不只播放文字，必须消耗时间或资源，并改变关系、记忆、承诺、线索或后续事件。
3. **正典可信**：使用 Alicization 的真实事件顺序作为主线骨架；原创内容只能补足日常、活动和人物表达，不能替换关键事实。
4. **即时反馈**：移动、点击、小游戏、奖励、失败、对话和战斗都必须有可见、可听、可理解的反馈。
5. **长期可扩展**：地图、事件、活动、角色、战斗、资产和 QA 都采用稳定 ID 与数据驱动结构，避免为每个新内容重写核心系统。

## 3. 参考作品的使用方式

本项目只提取可观察的设计方法，不复制任何作品的文字、美术、角色、关卡、UI、数值或音乐。

### 3.1 交互与活动

参考《夏日幻想曲》这类日程型生活叙事游戏的以下方法：

- 日程、地点、天气、时间段和人物关系共同决定可用活动。
- 活动短而具体，玩家能在几十秒内完成一次判断并看到结果。
- 同一地点可重复访问，但不同日期、关系和线索会改变内容。
- 生活活动与主线调查相互供给，不把日常做成无关的点击填充。
- 玩家在一天结束时看到“今天做了什么、谁记住了什么、明天会发生什么”。

UW 不复制其角色、文本、地图、数值或事件结构；所有内容必须转换为卢利特村、巨神树、禁忌目录和尽头山脉语境。

### 3.2 视觉语言

参考《蛋蛋糖》《造梦西游》所代表的清晰、明快、易识别的 2D 游戏表现方向：

- 角色轮廓清楚，缩小后仍能区分身份和动作。
- 色彩有层次，正常村庄偏温暖自然，异常和危险使用局部冷色或不自然的运动变化。
- 地图、人物、UI、特效和背景属于同一世界，不把几张写实背景和像素 token 随意拼接。
- 画面优先服务导航、操作和反馈，不使用复杂装饰遮挡玩法信息。
- 允许手绘、卡通、像素和轻动画共存，但必须由统一的比例、轮廓、光照和色彩规则约束。

不得在生成提示词中直接要求模仿上述作品的原画、角色或 UI；必须使用原创的可观察属性描述。

### 3.3 经典 RPG 的机制基准

项目学习成熟 RPG 的可验证方法，不堆叠作品名称或照搬系统：

- **塞尔达式可读交互**：重要物体、危险和路径在玩家行动前可识别，探索奖励通过环境和反馈表达。
- **勇者斗恶龙式信息清晰**：目标、资源、状态和结果使用稳定语言，主流程不要求玩家查外部攻略。
- **Chrono Trigger 式节奏**：减少无意义往返和随机拖延，让战斗、探索和剧情都推动状态变化。
- **Persona/生活 RPG 式日程判断**：时间段和关系制造取舍，但错过一次活动不会永久破坏通关。
- **成熟独立 RPG 的恢复设计**：失败后快速重试，低资源时总有明确恢复路径，难度来自判断而非信息隐藏。

所有借鉴都必须先写成“玩家问题 -> 机制 -> 可观察验收”，不能因为经典作品有某个系统就直接加入。

## 4. 正典与改编边界

### 4.1 第一阶段固定主线

```text
卢利特村三人日常
→ 巨神树天职
→ 谈及禁忌目录与尽头山脉
→ 三人前往洞窟
→ 接触暗黑界一侧的受伤者
→ 爱丽丝为施救触碰/越过边界
→ 三人返回卢利特村
→ 整合骑士在村中宣告罪名
→ 爱丽丝与家人、桐人、尤吉欧告别
→ 爱丽丝被带往中央大教堂
```

第一阶段终点固定为 `alice_captured` 或 `precapture_alice_captured`，只能有一个正式终点。玩家可以改变准备、关系、证据、承诺、回忆和最后表达，不能改变爱丽丝最终被带走。

### 4.2 内容分层

- **A：官方页面明确**。例如卢利特村、巨神树、禁忌目录、尽头山脉、爱丽丝身份和整合骑士体系。
- **B：原作/动画明确但当前官方摘要未覆盖**。例如洞窟遭遇受伤者、爱丽丝因施救越界、返回村庄后被带走。B 类必须忠实还原，不得当作自由留白。
- **C：项目原创补充**。例如可重复生活活动、村民日常、支线线索、关系回响和小游戏。C 类不能替换 A/B 主线。

当前 `materials/inbox` 中的 Pre-Capture 文档是候选资料，不是正式剧情源。正式接入前必须经过我审核、合并和连续性校验。

## 5. 核心循环

```text
查看今日目标
→ 移动到地点
→ 观察、对话或参加活动
→ 在成本与收益之间做选择
→ 获得即时结果
→ 写入关系、记忆、承诺、线索或紧张
→ 回到生活场景
→ 完成日结算
→ 解锁下一日内容
```

每个重要活动至少包含：

- 进入条件和地点；
- 操作方式或判断方式；
- 时间、HP、MP、体力或道具成本；
- 玩家可理解的收益和风险；
- 当下结果反馈；
- 至少一个后续回响；
- 失败或低资源时的恢复路径。

## 6. 战斗与角色动作基线

战斗暂不作为当前 Pre-Capture 交付阻塞，但从现在起所有角色和资产必须按后续战斗扩展预留。

### 6.1 战斗方向

第一版战斗采用短时、易理解、可暂停的 2D RPG 战斗：

- 小规模战斗场景，而不是无边界刷怪。
- 角色拥有普通攻击、防御/回避、技能、协同和撤退等明确行为。
- 战斗结果影响资源、关系、承诺和后续事件，不只改变经验值。
- 战斗必须支持失败、撤退、重新尝试和低难度体验。
- 规则由后端或独立战斗规则模块权威结算，Phaser 只表现输入、动画和反馈。

具体采用实时、半实时还是指令制，等第一阶段生活与探索垂直切片稳定后，通过独立战斗原型决定；不在当前剧情文件中临时发明半成品战斗。

### 6.2 战斗原型决策门

候选制式必须使用同一场景、同一角色和同一敌人做可比测试，并按以下指标评审：

- 新玩家 90 秒内是否理解攻击、防御/回避、技能和撤退；
- 桌面与触控是否都能稳定操作，是否需要过多同时按键；
- 敌方意图、命中、受击、资源消耗和失败原因是否清晰；
- 一场普通战斗的时长、重复度和重试成本是否合理；
- 每新增一个角色/敌人的动作、VFX、音频、数值和 QA 成本是否可持续；
- 战斗结果是否能通过事件接口影响资源、关系和剧情，而不侵入主线代码。

原型通过前不承诺正式制式；通过后必须形成 ADR、动作清单、数值 schema、存档迁移和自动测试计划。

### 6.3 每个可战斗角色的最低动作集

- idle：至少 2 帧或等价呼吸动作；
- walk：四方向，至少 4–6 帧；
- interact：读书、递物、挥斧或施术等角色专属动作；
- attack：普通攻击；
- skill/cast：技能或神圣术动作；
- hit：受击反馈；
- recover：起身、恢复或撤退；
- defeat/escape：失败或离场动作；
- face direction：动作结束后保持朝向；
- foot anchor：所有 Sprite 脚底锚点统一。

贴图不是“把静态人物贴到地图上”。角色表现必须同时考虑 Sprite、帧动画、脚底阴影、朝向、动作时长、碰撞框、特效、音效和 UI 状态。

## 7. 资产体系

正式资产分为六层：

1. **环境**：地图、地块、建筑、室内、天气、远景和可交互物件。
2. **角色**：肖像、四方向 Sprite、动作帧、阴影、表情和服装变体。
3. **UI**：图标、按钮、面板、状态条、任务标记、对话框和移动端布局。
4. **特效**：神圣术、边界异常、关系回响、奖励、受击、移动和环境粒子。
5. **音频**：BGM、环境声、脚步、活动音、UI 音、战斗音和结果音。
6. **数据**：manifest、sidecar、帧索引、碰撞框、锚点、运行时压缩版本和回滚记录。

生成图像智能体只负责素材交付，不负责修改剧情、代码、正式运行时目录或世界状态。所有视觉素材先进入 `materials/inbox`，通过风格、技术、权利和游戏内测试后再进入 `approved` 和 runtime。

### 7.1 生产管线与工具要求

每项正式资产按 `request -> 生成/绘制 -> sidecar -> 技术检查 -> 风格审核 -> 游戏内截图 -> approved -> runtime` 流转。至少保留源文件、运行时压缩件、版本号、hash、用途、权利和回滚记录。

- 地图使用可重复 tile、遮挡层、碰撞层、前景层、交互点和导航数据，不能只交付一张不可走的背景图。
- Sprite 图集必须登记帧尺寸、方向、动作名、FPS、循环、脚底锚点和碰撞盒；批处理工具负责图集打包与缺帧检查。
- UI 图标、VFX 和音频必须有状态/触发清单；静音、加载失败和低性能模式均有替代表达。
- 运行时不得直接扫描候选目录；只有 manifest 中已批准且 hash 匹配的资产可以接入。
- 每批资产先做一处代表场景的游戏内验收，再批量生产同类内容，避免整批风格或规格返工。

## 8. 技术框架

当前技术栈保留：

- Vue 3：界面、面板、对话、活动和 HUD；
- Phaser 3：2D 地图、角色表现、输入、动画和特效；
- FastAPI + Session：世界状态、剧情、关系、记忆、资源和存档权威；
- JSON/CSV/Markdown：数据驱动内容、素材台账和作者工作流。

当前不迁移 Cocos、不改成全 3D、不引入联网多人。只有当独立战斗原型证明现有 Phaser 表现不足时，才评估专用物理或战斗库；不为“看起来成熟”而增加无必要依赖。

新增系统必须遵守：

- 后端权威，前端不直接写永久事实；
- 内容与代码分离；
- scripted 模式始终完整可玩；
- hybrid/agent 只能提供候选表达或意图，不能改写结算；
- 新字段必须有存档默认值、API 契约和测试；
- 新战斗必须独立于 `FieldSlice.vue`，通过规则模块和事件接口接入。

## 9. 大众化与可访问性基线

- 新玩家 60 秒内完成第一次有效互动；同屏只突出一个主行动，其余信息按需展开。
- 关键状态不得只依靠颜色、声音或快速动画表达；文本、图标和形状至少提供一种冗余线索。
- 字号、对比度、键盘焦点、触控目标和长文本换行在桌面与移动视口均可用。
- 提供独立的音乐/环境/音效音量，以及降低闪烁、镜头震动和动画强度的设置。
- 主线失败允许快速重试或低难度辅助；辅助选项不惩罚剧情内容和存档。
- 首屏加载、图集、音频和 Phaser chunk 建立预算，以实机数据决定懒加载和降级，不凭感觉增加依赖。

## 10. 版本顺序

### 0.5.0-pre-capture：正典垂直切片

- 清理并合并 Pre-Capture 文档；
- 完成四幕 8–12 个关键节点；
- 接入固定抓捕终点；
- 维持现有生活活动、关系和记忆系统；
- 只补完成主线所需的地点和视觉反馈；
- 通过真人盲测。

### 0.6.x：生活系统与表现成熟化

- 日程、天气、地点活动和关系回访扩展；
- 角色 Sprite、表情、动作和环境动画统一；
- 统一音频层级、资源加载和移动端预算；
- 增加重复游玩中的路线差异。

### 0.7.x：战斗原型

- 单独制作战斗规则和战斗场景；
- 完成桐人、尤吉欧、爱丽丝和一个敌人的完整动作集；
- 验证攻击、受击、技能、撤退、失败和结算；
- 通过独立测试后再接入主线。

### 0.8.x 及以后：章节化扩展

- 新地图和新章节；
- 角色成长、装备和更丰富的战斗；
- 继续保持每章独立可玩、可存档、可回放和可测试。

## 11. 当前不做

- 不继续无目的扩写 Day 118+；
- 不把未经审核的 v001/v002 文本直接写进 `data/story`；
- 不先做完整大地图、完整战斗和几十个角色动作包；
- 不用图片生成结果掩盖剧情和玩法缺口；
- 不把“测试通过”当作“正典和美术已经通过”；
- 不删除原始素材审计记录，但旧稿不能作为正式依据。

## 12. 完成判定

第一阶段只有同时满足以下条件才算完成：

- 新玩家能在 60 秒内完成第一次有效互动；
- 玩家能理解当天目标、一次行动代价和一次行动收益；
- 至少三次选择产生跨节点回响；
- 四幕主线按正典顺序运行到爱丽丝被带走；
- 抓捕后状态真正终止，不被后续系统覆盖；
- 角色、地图、UI、活动和反馈在桌面与移动端不互相遮挡；
- scripted 模式无需外部 API 完整通关；
- 后端、前端、构建、E2E、素材和真人试玩均有证据。
